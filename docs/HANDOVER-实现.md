## 已确定的产品要求

项目采用 monorepo，最终安装一个 `Meno.app`；子应用是独立维护的完整功能模块，包含自己的界面、业务、数据和后台运行逻辑，不需要分别安装独立 `.app`。首版共享宿主进程，模块之间通过统一协议接入。

宿主以 macOS 菜单栏托盘为主入口，每个子应用是一行可点击的选项，右侧提供独立启停开关。点击名称打开该子应用自己的桌面窗口，重复打开时复用窗口并带到前台。窗口关闭和后台停用是两个独立动作。

第一个子应用是“到点提醒”。窗口必须能清楚查看所有提醒的时间点，快速创建是主要交互：输入内容、选择快捷时间或精确时间、选择提醒类型，然后回车保存；备注和复杂设置放在展开区域。App 不使用 AI 解析内容，也不需要模型密钥或模型服务。

每条事项独立选择 `system` 系统通知或 `fullscreen` 全屏提醒，列表中显示类型。同一条事项一次触发只使用所选类型，不能同时弹两种提示。全屏提醒参考用户提供的图片一、二，通过全局文字和柔和蒙层提示；整体配色与质感参考图片三的低饱和灰调、圆润形状和舒适留白。

外部 AI 可以通过 MCP 创建、查询、修改和取消提醒。自然语言理解发生在外部 AI 客户端，Meno 接收确定参数并校验、保存、执行，返回实际时间和运行状态。外部 AI 客户端关闭后，已启用的 Meno 继续负责提醒。

宿主只负责发现已注册模块、管理运行状态和窗口、转发业务命令，不直接实现提醒规则。提醒业务服务由界面、MCP 和 CLI 共用，统一完成参数校验、数据事务、状态变更和调度通知。

把模块定义、数据服务、窗口和后台运行时分开。关闭后台时必须等待正在进行的调度操作收敛，取消定时器、观察者、待展示队列、全屏面板和该模块的待触发系统通知。之后到达的异步回调不能重新创建任务；其他模块的任务不能被误删。

现有 `com.meno.app` 是宿主 Bundle ID，`com.meno.reminders` 是提醒模块 ID。建议保留为集中定义的稳定标识，接口和持久化统一使用；CLI 的 `reminders` 可作为显式别名。

## 提醒数据与运行规则

至少区分三种状态：子应用后台是否运行、单条提醒是否启用、某次触发是否已提交或处理。不要用一个 `enabled` 或 `completed` 字段同时表达它们。

提醒定义包含 ID、标题、备注、类型、单条启用状态、时间规则、时区策略、来源、创建和更新时间。触发实例包含所属提醒、原定时间、提交或展示状态、确认和延期结果；幂等记录保存请求标识、规范化参数与原写入结果。具体表结构由实现者定义并提供 schema version 和迁移策略。

相对时间在创建时解析成确定的绝对时刻。单次提醒保存绝对时刻；每天及周一至周五按当地墙上时钟计算，时区变化后重算。夏令时不存在的时间顺延至下一个有效时刻，重复出现的时间当天只触发一次。延期生成独立触发实例，不让周期整体后移。

系统通知通过 `UNUserNotificationCenter` 安排，全屏提醒由宿主进程内调度器和 AppKit 面板执行。系统通知已提交不表示用户已看到，通知被关闭也不表示事项已完成。通知权限缺失时可以保存事项，但必须展示受阻原因；不能自动切换成全屏类型。全屏提醒不依赖通知授权。

改变类型、时间、内容或取消事项时，根据稳定的标识撤销旧计划并同步新计划。数据写入成功和调度成功分别记录，发生调度错误时保留事项并显示可恢复的状态，不能把失败包装成已正常运行。

若接手环境存在旧 `reminders.json`，迁移时保留备份，旧提醒可默认迁移为系统通知；损坏文件应报告具体问题，不能静默清空。旧骨架中的 60 个通知请求限制属于当前实现策略，不是已确定的产品需求，后续需要明确容量与滚动安排方式。

## MCP 首版接口

使用标准 MCP 和官方 Swift SDK，依赖版本在实现时锁定。随 App 打包 `meno-mcp` 辅助程序，客户端通过 stdio 启动它；它再通过本机 Unix domain socket 调用宿主，不直接写数据库。标准输出只写协议消息，日志写标准错误。

宿主是唯一的业务写入方，多个 MCP 客户端可以各有桥接进程，最终汇聚到同一宿主。IPC 应校验协议版本和当前用户访问范围，正确处理宿主尚未启动、过期 socket、连接中断和调用超时。实际业务调用可自动后台启动宿主，单纯连接或工具发现不得自动启用提醒运行时。

| 工具 | 最小输入与行为 |
| --- | --- |
| `reminders_create` | `title`、`schedule`、`requestId`；可选 `reminderType`、`note`、`enablePlugin` |
| `reminders_list` | 按日期、状态、类型筛选，支持分页 |
| `reminders_update` | 提醒 ID、修改字段、`requestId`；未传字段保持原值 |
| `reminders_cancel` | 提醒 ID、`requestId`；取消未来触发，保留历史 |
| `apps_get_status` | 模块 ID；返回后台状态、通知权限和受阻原因 |
| `apps_set_enabled` | 模块 ID、目标启用状态、`requestId`；明确启停后台 |

`reminderType` 仅接受 `system` 或 `fullscreen`，省略时采用应用默认值，并在回执中返回实际类型。`enablePlugin` 默认 `false`；创建事项不会隐式打开被用户停用的后台。

时间结构采用互斥分支：`once + at` 表示带时区的 ISO 8601 绝对时间，`delay + afterSeconds` 表示正数延迟，`daily + time` 和 `weekdays + time` 表示按本地时区运行的固定钟点。非法、冲突或过去的单次时间返回明确错误，不在 App 内猜测用户意图。

工具调用示例：

```json
{
  "name": "reminders_create",
  "arguments": {
    "title": "喝水",
    "reminderType": "fullscreen",
    "schedule": { "kind": "delay", "afterSeconds": 1200 },
    "enablePlugin": true,
    "requestId": "drink-water-001"
  }
}
```

本例显式要求启用后台；若只需保存则省略 `enablePlugin`。写入成功后至少返回提醒 ID、`saved`、`armed`、实际类型、`nextTriggerAt` 和 `blockedReason`。`armed` 只有在后台运行、单条启用、存在未来触发点且类型所需条件满足时才为真；系统通知受操作系统展示策略影响，不能据此承诺用户一定看到。

保存成功但后台停用或通知未授权，应返回 `saved: true, armed: false` 和原因，工具本身不伪装成执行失败，也不声称已经启用。非法输入、存储失败等业务错误返回明确错误结果；MCP 工具业务错误使用 `isError`，CLI 使用非零退出码。调度提交失败应返回 `saved: true, armed: false` 和调度原因，便于安全恢复。

所有写工具要求 `requestId`：相同 ID 与相同参数重试不重复写入，也不重新计算相对时间；不同参数复用同一 ID 返回冲突错误。幂等记录与业务变更在同一事务中提交。重试保留原写入结果，但 `armed` 等当前运行状态需要重新查询，避免原操作成功后插件被停用，仍向外部 AI 返回过期的运行状态。

MCP 客户端关闭只断开控制入口，不停止 Meno 的后台提醒。设置页和文档提供准确的辅助程序路径与接入说明，不在未获用户请求时修改其他 AI 客户端的全局配置。

| A08 | 同时到点和延期 | 全屏事项不会堆叠遮罩，确认作用于正确实例，延期不改变重复周期 |

| A10 | 权限拒绝 | 系统事项能保存且展示受阻原因，全屏事项仍可按其类型工作 |
| A11 | 休眠、锁屏、时区、夏令时、重启 | 按各自规则重算与恢复，避免错误补发或重复实例 |
| A12 | 标准 MCP 接入 | 真实客户端可以发现并调用六个首版工具，两种类型均可创建，界面及时更新 |
| A13 | 幂等和超时重试 | 相同请求只产生一次写入，保留第一次解析的时间，不同参数复用 ID 明确报错 |
| A14 | MCP 断开与宿主重启 | 客户端断开不停止已启用提醒；宿主未运行时业务调用可后台启动并返回准确状态 |
| A15 | 持久化异常 | 不丢失已有数据、不静默清空文件，失败回执与界面一致 |
| A16 | 可安装运行 | 真正的 `.app` 可启动，通知和辅助程序路径在打包后有效，登录启动可启停 |

自动化重点覆盖状态和并发、时间规则、类型切换、业务校验、迁移、事务、幂等与协议契约。视觉、权限、通知真实送达和系统窗口行为需要真实 `.app` 与真机验证，不能用 mock 测试替代。
